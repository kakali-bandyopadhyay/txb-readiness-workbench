# ADR-001: Locking strategy for readiness action updates

- Status: Accepted for the current prototype.
- Context: API and web updates can target the same `readiness_action` row. A detached read-modify-write can otherwise overwrite another writer's newer row state.
- Decision: Use PostgreSQL optimistic locking through JPA `@Version` for normal updates. Retry an optimistic conflict for at most five total attempts with a 2, 4, 8, then 16 ms cap and half-to-full jitter. Log each writer that exhausts the bound and return HTTP 409 to API callers. Keep an explicit `PESSIMISTIC_WRITE` path in the integration benchmark for comparison. An optional 64-stripe fair in-process retry gate is available through `READINESS_ACTION_OPTIMISTIC_RETRY_GATE_ENABLED`, defaulting to `false`; benchmarks compare optimistic updates with that gate disabled against pessimistic updates.
- Rationale: Readiness updates are expected to have low contention, so optimistic locking avoids holding a database lock while applying ordinary patches. If contention is sustained, optimistic retries increase latency and can exhaust the bound; pessimistic locking serializes writers and may increase waiting or deadlock exposure when transactions lock rows in different orders.
- Evidence: `WorkbenchIntegrationTest.readinessActionConcurrentUpdatesAreNotLostAndCompareLockModes` performs one unmeasured 50-writer warm-up, then runs five measured pairs with alternating lock-mode order against Testcontainers PostgreSQL. Findings report three pure optimistic invocation medians and the full range after the gate-disabled runs complete.
- Gate scope: This mitigation only serializes retries within one JVM. Multiple application instances do not share the gate; the database `@Version` check remains necessary for cross-instance correctness. Gated measurements are a separate mitigation variant, not the pure optimistic baseline.
- Scope: Synthetic prototype data and workload only; this is not evidence of bank-scale behavior.
